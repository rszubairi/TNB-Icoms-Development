Build Plan Review — ICOMS 2.0

Four modules, one grid.

Validation of IMPLEMENTATION_PLAN.md against the four URS documents and the database design doc, plus a task-level breakdown for everything still ahead.

Repo state checked: src/ + frontend/src/app Schema: 31 tables, fully scaffolded Built: Auth + Users/Roles/Zones only

Is the plan sound?

Yes, directionally — the phase order (Setup → Requestor/Planner → TOMS → GNC → Reporting) matches the dependency chain in the URS: nothing in Module 2 works without zones/stations/equipment from Module 1, and nothing in Module 3/4 works without an outage record from Module 2.

But it's too coarse to build from. Each "Phase" in the current plan is a paragraph covering an entire URS module — dozens of screens, workflow states, and background jobs collapsed into 3–4 bullets. It also has two gaps worth fixing before work continues: it never explicitly schedules Organisation / Station / Equipment / Voltage / Off-Point / Dropdown / Outage-Type-Rule admin CRUD (Module 1 §5.2.1–5.2.15), which Module 2's outage form depends on entirely — and it doesn't mention the code already scaffolded for the full DB schema being 4 modules ahead of the controllers/UI.

The breakdown below re-derives each phase into concrete backend + frontend task lists, checked line-by-line against the URS status matrices, field tables, and workflow steps — so gaps like "DSO auto-agree after 7 days" or "KIV auto-timeout at 31 days" don't get silently dropped between the plan and the sprint board.

00Cross-Cutting Foundations

Mostly todo

Infrastructure every module depends on, but that the phased plan never calls out as its own workstream. Build these alongside Phase 1, not after it.

Background job runner Hangfire / IHostedService

  • Stand up the scheduler now — 7 of the automated workflow rules in the DB design doc (§11) fire on Module 2/3 outages, so the runner needs to exist before those modules land, not be retrofitted.
  • Unconfirmed auto-close: RequestorStatus → Outage Closed – Unconfirmed, 2 weeks before start
  • DSO auto-agree: PlannerStatus → Agreed after 7 days pushed, flag DsoAgreedBySystem
  • KIV auto-timeout: GnmStatus → Outage Closed – KIV Timeout after 31 days
  • Pending auto-KIV: GnmStatus → KIV, 24h after start with no GNM action
  • Not Taken auto-close: GncStatus → Outage Closed – Not Taken, 5 days after end with no Taken-Active
  • GCU reminder: email 2 days before outage start to all GcuAcknowledgement rows
  • Every job writes to audit.AuditLog — build the writer once, reuse everywhere

Email + notification layer

  • IEmailSender abstraction with Resend implementation (per plan) — confirm templates for: user onboarding, role-transfer request, PIC creation/update, GNM→GCU notify, GNC authorisation/un-authorisation (exact subject/body given in Module 1 §5.2.10), change-request approve/reject, SLD/CommMemo stage transitions
  • SignalR hub for docket/handover live sync (per plan stack) — needed by TOMS docket (Module 3) and GNC Handover (Module 4) real-time views

File storage

  • FileStorageService abstraction over Azure Blob / network share for SLD PDFs, Contingency Plans, Comm Memo attachments, Handover exports
  • Enforce PDF/Word-only uploads with size caps where URS specifies (Switching Program: pdf+word, multi-file)
Row-level zone security (DB doc §10.3) — every list/query needs a mandatory WHERE ZoneId = @UserZoneId except for GNM ADMIN/SysAdmin. This is a cross-cutting concern best built as a global EF Core query filter or API-layer policy now, not bolted onto each controller later.
